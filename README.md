# Doomcure — doomcure.com

Production site for Doomcure, an antidote to doomscrolling. It's a faithful port of the approved homepage design plus the waitlist backend.

Everything lives in one Next.js 16 app in [`web/`](web/). The waitlist is handled by a **Server Action** in the same app, so there is no separate API service. It writes to Postgres (Neon) and sends emails through Resend. This is the same setup as squarebookai.

## Sections and what runs in the browser

Sections are Server Components and ship no JavaScript, except the interactive pieces marked "client" below.

| Section | Component | Client JS |
|---|---|---|
| Nav | `Nav` | none |
| Hero | `Hero` (server), with `PhoneSplit` (DOOM/CURE slider + auto-sweep) and `WaitlistForm` | client: `PhoneSplit`, `WaitlistForm` |
| Marquee | `Marquee` | `Offscreen` only (pauses the loop when off-screen) |
| Problem | `Problem` (server), with `MeterValue`/`MeterRuler` | client: meter |
| Idea | `Idea` (server), with `CardDeck` | client: `CardDeck` |
| Story | `Story` (server), with `StoryArrows` | client: `StoryArrows` |
| Founder, Footer | `Founder`, `Footer` | none |
| Waitlist | `Waitlist` (server), with `WaitlistForm` | client: `WaitlistForm` |
| Scroll pill | `ScrollMeterPill` | client |

`Offscreen` is a tiny IntersectionObserver wrapper. While its content is off-screen it sets `data-offscreen`, which pauses the marquee, the phone feeds and the grain.

## Local setup

Requirements: Node 20.9 or later, and a Postgres database.

```bash
cd web
npm install
cp .env.example .env.local      # then fill in the values
npm run db:migrate              # creates the waitlist_signups table
npm run dev                     # http://localhost:3000
```

Postgres for local work, pick one:

- **Docker:** `docker run --name doomcure-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=doomcure -p 5432:5432 -d postgres:17`. This matches the default `DATABASE_URL` in `.env.example`.
- **Neon:** create a free project and use a dev branch's connection string.

If `RESEND_API_KEY` is empty, the forms still work and the emails are skipped with a log line.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | yes | Postgres connection string. Use Neon's **pooled** URL on Vercel. Without it, the forms show an error asking people to email instead. |
| `IP_HASH_SALT` | yes in production | Random string (`openssl rand -hex 32`). IPs are stored only as salted hashes, for rate limiting. |
| `RESEND_API_KEY` | for email | From resend.com → API Keys. |
| `EMAIL_FROM` | for email | `Doomcure <support@doomcureai.com>`. The domain (`doomcureai.com`) must be verified in Resend. |
| `NOTIFY_EMAIL` | for email | Inbox that receives each new signup. |
| `NEXT_PUBLIC_SITE_URL` | no | Defaults to `https://doomcure.com`. Used for canonical URLs, sitemap and OG tags. |

## How the waitlist works

1. Both forms (hero and CTA) call the `joinWaitlist` Server Action (`src/app/actions/waitlist.ts`) with `{ email, source: "hero" | "cta", website }`.
2. If the honeypot field `website` is filled, the action returns a normal-looking success and stores nothing.
3. zod validates the input. The email is trimmed and lowercased before the format check.
4. Rate limit: 10 signups per IP per hour, counted in Postgres from `waitlist_signups` (indexed on `ip_hash, created_at`). This works across serverless instances.
5. The signup is stored in `waitlist_signups`: `id, email (unique), source, created_at, ip_hash, user_agent`. A duplicate email returns `already_joined`, which the UI treats as success. No error is shown and no second welcome email is sent.
6. Both emails are sent with `after()`, once the response has gone out: the welcome email ("You're on the list. More on this soon.") and the notification to `NOTIFY_EMAIL`. An email failure is logged and never fails the signup.
7. UI states: idle → submitting (button disabled + spinner, screen-reader announcement) → success (both forms switch to "You're on the list"; the CTA plays the card burst) or error (inline message saying what went wrong and to try again).

The Postgres pool (`src/lib/db/client.ts`) is created lazily, once per server instance. It's registered with `attachDatabasePool` from `@vercel/functions`, so idle connections close before a Fluid compute instance suspends.

## How the contact form works

`/contact` uses the same pattern as the waitlist. `ContactForm` posts to the `sendContactMessage` Server Action (`src/app/actions/contact.ts`) with `useActionState`, so it also works with JavaScript disabled.
- **Checks:** the same honeypot as the waitlist; zod validates name, email and a message of 10 to 5,000 characters; the limit is 5 messages per IP per hour.
- **Storage:** messages go into `contact_messages`.
- **Emails:** two are sent with `after()`. The message is forwarded to `NOTIFY_EMAIL` (reply-to is set to the sender), and the sender gets a short "We've got your message" acknowledgement.
- **UI states:** errors appear next to each field and keep what the person typed. On success, a confirmation panel with a tick replaces the form and receives focus.

`GET /api/waitlist/count` returns `{ count }`, cached for 60 seconds. It's for the founder and isn't linked anywhere on the site.

## Deploy to Vercel

1. Push the repo to GitHub, GitLab or Bitbucket, then in Vercel choose **Add New → Project** and import it.
2. Set **Root Directory** to `web`. The framework preset (Next.js) and the build command are detected automatically.
3. **Database:** Project → **Storage** → **Create Database** → **Neon (Postgres)**, and connect it to the project. This adds `DATABASE_URL` (and the other Neon variables) to the environments you choose.
4. Add `IP_HASH_SALT`, `RESEND_API_KEY`, `EMAIL_FROM` and `NOTIFY_EMAIL` under Settings → Environment Variables, for Production (and Preview if you want previews to send emails).
5. Run the migration once against the production database, from your machine:
   ```bash
   cd web
   DATABASE_URL="<Neon connection string from Vercel>" npm run db:migrate
   ```
   Repeat this whenever you add a migration. If you use Neon preview branches, run it against those as well.
6. Deploy. Preview deployments serve a `Disallow: /` robots.txt, so they stay out of search results.

## Connect doomcure.com (bought on GoDaddy)

### 1. Point the domain at Vercel
1. In Vercel: Project → **Settings → Domains** → add `doomcure.com`, then add `www.doomcure.com`. When asked, choose to **redirect `www` to the apex**. The canonical URLs, sitemap and OG tags all use `https://doomcure.com`.
2. Vercel then shows the exact DNS records to create. Use those values; they are typically:
   - apex `doomcure.com`: **A** record, host `@`, pointing to the IP Vercel shows (often `76.76.21.21`)
   - `www`: **CNAME** record, host `www`, pointing to the target Vercel shows (often `cname.vercel-dns.com`)
3. In GoDaddy: **My Products → doomcure.com → DNS → Manage DNS**.
   - Delete GoDaddy's default "Parked" **A** record for `@`, and any existing `www` CNAME, so they don't conflict.
   - Add the A and CNAME records exactly as Vercel shows them, with TTL 1 hour or lower.
4. Back in Vercel, wait for both domains to show **Valid Configuration**. HTTPS certificates are issued automatically.

No `api.doomcure.com` record is needed; the backend runs inside the same app.

### 2. Let Resend send as @doomcureai.com
1. In Resend: **Domains → Add Domain** → `doomcureai.com` (or a subdomain such as `mail.doomcureai.com`). The site lives on doomcure.com, but all email addresses are on doomcureai.com.
2. Resend lists the DNS records to add: an MX record and SPF TXT for the sending subdomain, a DKIM TXT record, and optionally DMARC. Add each one in the DNS manager for doomcureai.com exactly as shown, then click **Verify** in Resend.
3. Set `EMAIL_FROM` to an address on the verified domain.

To also *receive* mail at support@doomcureai.com and thennarasan@doomcureai.com, set up a mailbox provider (Google Workspace, Zoho, etc.) for doomcureai.com and add its MX records for `@`. Resend only sends.

### 3. Optional: dopaminedetox.ai → doomcure.com (301)
If you buy that domain, add `dopaminedetox.ai` (and `www.dopaminedetox.ai`) in the same Vercel project under **Settings → Domains**, choose **Redirect to `doomcure.com`** with **301 (Permanent)**, and point its DNS at Vercel with the records it shows. GoDaddy's own "Forwarding → 301" also works, but it doesn't keep paths.

## Fidelity notes (vs. the approved design, `Main.dc.html`)

Compared side by side in Chrome at 1440px and 390px:
- **Layout:** every section has the same top and height as in the design.
- **Pixel difference:** under 0.4% in every section except the CTA/footer, where the brand name changed.
- **Interactions:** all checked in the browser (slider auto-sweep and drag, scroll meter + pill, nav anchors under the sticky nav, card deck, story arrows, waitlist states).

Intentional differences:
- The brand is renamed Doomproof → Doomcure: wordmarks, sticker text, the DOOM/CURE label, the slider's aria-label and the footer. The first career card reads just "Founder & CEO", without the company name. The contact email is `support@doomcureai.com` everywhere, as a `mailto:` link. The founder card has Email (`thennarasan@doomcureai.com`) and LinkedIn buttons, as on squarebookai. Both also appear in the Organization JSON-LD.
- "Privacy · Terms" are links to the new pages, and a "Contact" link was added next to them. The footer's link rows sit above the giant wordmark (`z-index`), and the scroll pill ignores clicks (`pointer-events: none`). Without this, the wordmark's glyphs and the pill covered the legal links.
- Nav and footer links point to `/#section`, so they also work from the Privacy, Terms and Contact pages.
- The founder card shows the real photo in place of the `[Founder photo]` placeholder.
- **Story carousel:** it doesn't use CSS `scroll-behavior: smooth`. Together with scroll-snap, that made Chrome perform a smooth snap on load, which stopped LCP from ever being recorded (Lighthouse Performance: 0). The arrow buttons pass `behavior: "smooth"` themselves, so it looks the same.
- **Hero fade-ins:** they start at opacity .01 instead of 0. It looks identical, and Chrome can count the hero text as the LCP element.
- **Accessibility additions with no visual change:** a focus ring on the phone slider and the form pill, live regions for form status, and a visually hidden honeypot.

Kept as designed, worth a decision later:
- At 390px the nav wraps onto two lines.
- In the Story section, the tag and intro text are white on violet `#7B61FF` (contrast 4.2:1 and 3.5:1, below AA's 4.5:1).
